Each route is a Next.js App Router handler file under `src/app/api/<domain>/.../route.ts`, exposing named `GET`/`POST` exports. The module is organized by feature domain: `auth/[...nextauth]` delegates to NextAuth with lazy option building guarded by `isAuthConfigured`; `crm/deals` and `crm/leads` are read-only or write proxies through `serverCrmClient()` from `@/lib/bitrix-client`; `editor/media`, `editor/moderation`, and `editor/pages/[pageId]/{draft,publish}` proxy through `serverEditorClient()` from `@/lib/editor-client`; `health` aggregates dependency probes via `@jol-hub/observability`; `perf` ingests Web Vitals; `telemetry/errors` and `telemetry/perf` ingest client error and performance samples. Dependency direction is strictly inward: routes depend on shared libs (`@/lib/*`, `@jol-hub/*`) but never on UI components. All routes validate input first (Zod schemas or regex patterns), then check configuration (`isXxxConfigured`), then call a server client or forward via `fetch` to `BACKEND_API_URL`. Pilot mode (unconfigured backend) returns 204/503 instead of failing the caller. Tenant boundaries are enforced by validating `tenantSlug` against `SLUG_PATTERN` before forwarding as `X-Tenant` to the backend's RLS layer.
