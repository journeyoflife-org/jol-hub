Three Next.js App Router files form the outermost shell for every tenant page under `/{locale}/{tenant}`. `page.tsx` at `[locale]/page.tsx` is a dynamic route safety net: it validates the locale via `isSupportedLocale`, resolves the current tenant from headers/subdomain via `resolveCurrentTenant`, redirects to `/{locale}/{tenantId}` when present, otherwise calls `notFound()` to avoid tenant enumeration. The core layout in `[locale]/[tenant]/layout.tsx` is a server component that resolves the tenant by first loading a seed-data fixture (`loadTenantFixture`) and falling back to the STEP-5 registry (`findTenantBySlug`); unknown tenants trigger `notFound()`. It composes the effective message catalog by merging common(locale) with a vertical derived from either the fixture or `themeVerticalFor(registryTenant.vertical)`, then wraps children in `TranslationProvider` + `TenantProvider` (via `toPublicTenant`, which strips the schema so no internal model leaks to the client — ADR-001). The layout also assembles shared chrome: Header with nav built from fixture pages, Footer with legal links, SkipLink for WCAG 2.4.1, AuthSlot for login/logout, LocaleSwitcher, and CookieConsentBanner for GDPR/ePrivacy. `error.tsx` is a `'use client'` Next.js error boundary scoped to this layout; it catches rendering/data errors without crashing the app, logs the digest, reports via `reportError`, and renders a generic i18n-driven UI with retry and contact-support actions. Dependency direction flows inward: layout depends on `@jol-hub/i18n`, `@jol-hub/ui`, `@jol-hub/tenant-resolver`, and local libs (`content-loader`, `i18n-helpers`, `seo`, `tenant-context`, `template-registry`, `auth`), while the root page additionally depends on `tenant-resolver` for header-based resolution.
