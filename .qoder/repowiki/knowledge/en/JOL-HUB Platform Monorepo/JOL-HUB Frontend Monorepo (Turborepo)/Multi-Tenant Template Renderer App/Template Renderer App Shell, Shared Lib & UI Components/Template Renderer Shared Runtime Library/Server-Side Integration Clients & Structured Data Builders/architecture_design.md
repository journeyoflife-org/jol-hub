This leaf module groups four distinct server-side concerns under `frontend/apps/template-renderer/src/lib/`:
- Authentication boundary (`auth.ts`): a thin adapter over NextAuth's `getServerSession` plus the shared `@jol-hub/auth/oidc` package; exposes `isAuthConfigured` and `getAuthSession` which return `null` in pilot mode so pages render an unauthenticated state without breaking.
- Backend client bindings (`bitrix-client.ts`, `editor-client.ts`): each file instantiates a hub-backed SDK (`CrmBackendClient`, `EditorApiClient`) using `BACKEND_API_URL` (and `BACKEND_SERVICE_TOKEN` for the editor). Both expose an `isXxxConfigured()` guard and a `serverXxxClient()` factory returning `null` when the env var is absent, enforcing a pilot-mode pattern where callers must check configuration before use. Secrets never leave the server; browser code only hits same-origin `/api/*` proxies.
- Structured-data builders (`church-landing.ts`, `services-landing.ts`): pure functions that map tenant fixtures + verticals into JSON-LD entities via the shared `@jol-hub/seo` `churchEntity` builder and hand-rolled shapes (`FuneralHome`, `LocalBusiness`). They are data-driven — every emitted field comes from the fixture's `identity`/`name`, with no fabricated literals, and return `undefined` when required source data is missing.
Dependency direction is one-way: these modules depend on shared packages (`@jol-hub/auth/oidc`, `@jol-hub/bitrix-sdk`, `@jol-hub/seo`, `@jol-hub/i18n`, `@jol-hub/tenant-resolver`, `@jol-hub/seed-data`) and local helpers (`i18n-helpers`, `json-ld`), but nothing inside this scope imports from the app's page routes or components.
