Two parallel access paths coexist in one package:

- Legacy direct path: `src/client.ts` (`Bitrix24Client`) holds an OAuth access token and issues `fetch` calls to `<domain>/rest/<method>?auth=...`. It owns retry/backoff, timeout, batch requests, and throws typed errors from `src/errors.ts` (`Bitrix24ApiError`, `Bitrix24AuthError`, `Bitrix24RateLimitError`, `Bitrix24TimeoutError`). Each domain surface is a separate class under `src/api/` (`user`, `department`, `calendar`, `crm`, `events`, `email`) that receives the parent client via constructor injection.
- Preferred hub-backed path: `src/backend-client.ts` (`CrmBackendClient`) never touches Bitrix24 directly; it POSTs to `/crm/*` on a configurable `baseUrl`, attaching `X-Tenant` for RLS. It returns a discriminated union `CrmResult<T>` and classifies failures into a closed `CrmErrorKind` taxonomy (`unconfigured | auth-rotation | rate-limit | validation | server | network | timeout`) with idempotent GET retries and mutation-only-429 retries.
- React layer: `src/hooks.ts` (published as a separate subpath `@jol-hub/bitrix-sdk/hooks`) provides `useCrmLead`, `useCrmDeals`, `useCrmLeads`, `useCrmTasks`, `useCreateLead` built on a shared `useCrmQuery` primitive with optional polling and an in-memory lead cache. A module-scoped registry (`provideCrmClient`) lets consumers inject a default client so hooks can be used without explicit props.
- Barrel `src/index.ts` re-exports both paths plus all domain types from `src/crm-types.ts`, `src/types.ts`, and `src/api/*.ts`; UTM helpers live in `src/utm.ts`.
- Build: `tsup.config.ts` compiles two entry points (`src/index.ts`, `src/hooks.ts`) to ESM + CJS with `.d.ts` generation into `dist/`, matching the dual `exports` map in `package.json`.
