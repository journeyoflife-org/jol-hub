- Route groups are used to scope layouts and guards: `(auth)` for public auth pages and `(dashboard)` for protected admin sections, each with its own `layout.tsx` wrapping children in `AuthGuard`/`CountryGuard`.
- API clients are organized as named modules (`dashboardApi`, `parishesApi`, `usersApi`, `analyticsApi`, `aiApi`, `authApi`) in `src/lib/api.ts`, each exposing typed methods built on a shared `fetchApi` wrapper that attaches Bearer tokens and normalizes `{ success, data, error }` responses.
- Access control follows a 4-tier hierarchy (`super` → `country` → `diocese` → `facility`) enforced both at the middleware level (role map in `src/middleware.ts`) and at the data level via `canAccessEntity`/`canViewAggregatedData` in `src/lib/auth.ts`, with country-scoped data residency checked on every entity access.
- Environment-driven feature toggles are declared in `next.config.js` under `env` (e.g. `NEXT_PUBLIC_ENABLE_ANALYTICS`, `NEXT_PUBLIC_ENABLE_MOCK_DATA`, `NEXT_PUBLIC_DEFAULT_LOCALE`) and consumed via `process.env` throughout the app rather than runtime config objects.
- UI components follow a consistent shadcn/Radix pattern: small primitives live one file per component under `src/components/ui/` (button, card, dialog, table, etc.) and are re-exported or composed into higher-level domain components under feature folders like `components/entities`, `components/compliance`, `components/bitrix24`.
- Server-side security headers are centrally applied via `next.config.js` `headers()` returning `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Permissions-Policy` disabling camera/microphone/geolocation.
