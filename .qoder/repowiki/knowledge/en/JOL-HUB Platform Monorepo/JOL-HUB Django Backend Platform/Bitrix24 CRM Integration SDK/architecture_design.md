The module is organized as a layered SDK around a single `Bitrix24Client` (`client.py`) that owns HTTP transport (httpx), rate limiting, retry with exponential backoff, batch requests, token refresh, and exposes lazy-loaded sub-APIs via properties. The `api/` package contains one domain-per-file resource layer — `contacts.py`, `deals.py`, `events.py`, `email.py` — each defining typed dataclasses for request/response payloads plus an `XxxApi` class that calls `self._client.get/post(...)` with Bitrix24 method names like `crm.contact.add`. Cross-cutting concerns are split into two sibling packages: `audit/logger.py` implements a `ComplianceAuditLogger` that builds a SHA-256 hash chain of `AuditEntry` records (with periodic anchors every 1000 entries) for GDPR Art. 30 / PCI-DSS Requirement 10 compliance; `webhooks/handlers.py` defines a `WebhookHandler` with a register/dispatch table for Bitrix24 webhook events (`ONCRMCONTACTADD`, `ONCRMDEALUPDATE`, etc.), validates application tokens and HMAC signatures, and synchronizes changes into local `apps.crm.models` using `asgiref.sync.sync_to_async` to keep the webhook handler async while performing synchronous ORM writes. Dependency direction is strictly inward: webhooks → client APIs → `Bitrix24Client` → httpx; the audit logger has no dependency on the rest of the SDK beyond being invoked by it. The package root `__init__.py` re-exports only the public surface (`Bitrix24Client`, the four Api classes, `ComplianceAuditLogger`).
