Standard Django app under `apps.organizations` exposing a DRF REST API. `models.py` defines the domain: `Organization` (with Catholic/non-Catholic/commercial type enums, compliance levels, legal-hold flags, Bitrix24 CRM fields, and a 4-tier diocese→deanery→facility hierarchy via `parent_diocese`), `OrganizationMember` as a user↔organization junction with admin/editor/viewer roles, `Website` as a one-to-one config attached to an organization, and `ConsentSettings` for GDPR Art. 7/13 consent tracking. All models extend `apps.core.models.BaseModel`. Tenant isolation is enforced at the model layer by overriding `save()` on `OrganizationMember`, `Website`, and `ConsentSettings` to call `_validate_tenant_context()`, which reads the current tenant id from `apps.crm.middleware.get_current_tenant_id()` and raises a `ValidationError` if the target organization differs — imported lazily so the middleware dependency is optional. `views.py` provides DRF generic views (`ListCreateAPIView`, `RetrieveUpdateDestroyAPIView`) for organizations, per-organization website, and members; `serializers.py` separates read/write schemas via `OrganizationSerializer` vs `OrganizationCreateSerializer` (which auto-populates `slug` and `owner`). `urls.py` mounts routes under `organizations/` with UUID pk paths. `admin.py` registers all three models with list filters and search. Migrations live in `migrations/` and evolve the schema (e.g., adding `ConsentSettings`, Bitrix24 fields).
